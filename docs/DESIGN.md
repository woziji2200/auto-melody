# 项目设计

Auto Melody 的目标是根据音乐和目标难度生成 Malody 4K 谱面。它把节奏规划、轨道编排和人类短语检索组合起来，分别处理音乐落点与四轨写法。

使用方法见[快速开始](../README.md#快速开始)，重新训练的方法见[训练指南](TRAINING.md)。本文说明当前代码的工作方式。

## 为什么分开生成节奏和轨道

同一段音乐可以对应多种合理谱面。同一组落点既可以排成左右交替，也可以排成其他四轨组合；难度变化又会改变事件密度、同押和 Hold。因此，音乐落点与轨道写法虽然相关，却是不同层次的决策。

项目先生成不依赖具体轨道的节奏骨架，再为骨架选择轨道。这里的“事件”指同一时间点一起按下的音符组。例如，一个事件可以是双押，其中一个按键为 Hold。节奏骨架记录这个事件的时间、按键数、Hold 数和时长，轨道编排再决定它们落在哪些列。

这种拆分让轨道编排和后续检索在固定节奏的条件下工作，避免局部键型调整随意改变音乐落点。它是一种设计取舍，实际谱面仍需要玩家检查和调整。

## 生成流程

```text
OGG 音频 + 用户提供的 BPM / beat zero + 目标难度
                       │
                       ▼
         MERT 音频特征 + 频谱与瞬态特征
                       │
                       ▼
         显著性模型：给候选落点打分
                       │
                       ▼
         节奏规划模型：生成节奏骨架
                       │
                       ▼
         轨道编排模型：生成四轨动作序列
                       │
                       ▼
         人类短语检索：替换兼容的局部写法
                       │
                       ▼
         导出谱面、音频、可选封面与生成报告
```

### 1. 音频表示与显著性

MERT 是冻结的预训练音频编码器，负责将音乐转换成音频特征。显著性模型还使用 log-mel 频谱与谱通量特征补充局部能量和瞬态变化，并结合拍内位置及目标难度，为候选时间点打分。MERT 在项目的训练过程中不更新参数。

显著性训练使用同一首歌多张谱面的落点信息：对某张目标谱面，与其难度越接近的谱面权重越高，多个谱面共同出现的落点获得更高的支持值。这是模型名称中“共识”的含义；该支持值来自人工谱面，不能等同于音乐中唯一正确的落点。

推理时不需要输入歌曲的人工谱面，只需要音频、时间网格和目标难度。

### 2. 节奏规划

节奏模型读取冻结的显著性表示，用局部时序模块处理相邻候选，再用小节级 Transformer 汇总长程上下文。它预测：

- 每小节的事件数量；
- 各候选落点的分数；
- 每个选中事件的按键数和 Hold 数；
- Hold 的持续时长。

解码时，先根据预测数量，在每小节按落点分数选取 top-k 候选，再采样事件类型并转换 Hold 时长。此时仍未决定最终轨道。

### 3. 轨道编排

轨道模型是自回归模型，依据节奏骨架、目标难度和已生成的动作逐事件安排四条轨道。每条轨道可为空、普通按键或 Hold 起点，四条轨道的非空组合构成 80 种动作。

采样会约束动作的按键数与 Hold 数，使其符合骨架，并根据进行中的 Hold 限制轨道选择。这一阶段产出完整的轨道编排，也是检索没有兼容结果时使用的方案。

### 4. 人类短语检索

检索库把训练谱面按四拍小节组织。每个短语保存该小节的轨道动作，以及对应音乐的 MERT 特征。检索分两步：

1. 根据事件顺序及每个事件的按键数、Hold 数筛选兼容短语；
2. 在兼容短语中选择音频特征余弦相似度最高的一项。

找到短语后，程序把其中的轨道动作应用到当前生成的事件上；没有兼容短语则保留轨道模型的结果。这不是检索整张谱面，也不会把来源谱面的音符时间复制到当前歌曲。

兼容条件并不要求来源短语与当前小节具有完全相同的事件间隔。当前实现保留生成的事件时间、每事件按键数、Hold 数和时长，替换的是轨道写法。因此，检索是利用已有写法的补充手段，不是对节奏匹配或可玩性的保证。

### 5. 导出与检查

程序将多个目标难度的谱面、原始音频和可选封面打包到一个 MCZ。导出后重新读取谱面，核对事件时间、按键数和 Hold 数是否与节奏骨架一致，并写出同名 JSON 报告。

报告包括结构检查、统计信息和检索覆盖情况。通过这些检查说明相应结构被保留，不等于通过玩家评价或保证生成效果。

## 模型与索引的分工

| 资产 | 用途 |
| --- | --- |
| `data/MERT/` | 冻结的音频特征编码器 |
| `data/consensus-salience-v1.pt` | 学习候选时间点的难度相关显著性 |
| `data/consensus-rhythm-planner-v1.pt` | 规划事件数量、落点、类型和 Hold 时长 |
| `data/lane-arranger-v2.pt` | 将节奏骨架编排到四条轨道 |
| `data/rhythm-train.pt` | 保存训练谱面的事件记录，供构建短语库使用 |
| `data/phrase-features.pt` | 保存训练歌曲的小节级音频特征，供短语检索使用 |

最后两项是训练数据派生的检索资产，不是神经网络权重。直接使用项目时，模型和检索资产都需要准备齐全；无需重新训练或提供原始训练集。

## 训练如何对应生成流程

训练分为三个阶段：先训练显著性模型，再冻结它训练节奏模型，最后用人工谱面的节奏骨架训练轨道模型。MERT 始终冻结；短语库则从训练集构建，不是第四个训练阶段。

预处理按音频 fingerprint 分组划分 train、validation 和 test，使同一音频的不同难度进入同一个划分。推理短语库只使用训练划分，避免把验证或测试谱面的人工写法放入检索库。训练命令与产物说明见[训练指南](TRAINING.md)。

## 当前实现边界

- 公开推理入口接受 OGG，要求用户提供恒定 BPM 和 beat zero；它不自动分析拍速，也不提供变速时间线输入。
- 内部候选网格为每拍 24 ticks，以四拍为一个聚合与检索单位，不能直接视为任意拍号的乐句分析。
- 目标难度参与模型条件输入，但不保证与每位玩家的主观难度一致，也不强制不同难度的事件集合互相包含。
- 短语检索不会重新执行轨道模型的逐步 Hold 占用约束；结构保留检查不覆盖所有最终轨道冲突，生成后仍需检查实际可玩性。
- 固定随机种子便于复现采样，但不保证不同硬件和依赖环境得到逐位相同结果。
